## 二、三个方向的详细判断与建议

### 2.1 Agent 开发：从 chatbot → ReAct Agent

**当前状态：**
- [`ChatService`](app/services/chat_service.py:36) 是 stateless chatbot，只做单轮 QA
- 没有 tool 定义，没有推理循环，没有状态管理

**建议实现：**

| 工具 | 对应 API | 面试价值 |
|------|----------|----------|
| `get_product_info(product_id)` | `GET /api/v1/products/{id}` | 商品查询工具 |
| `get_order_status(order_id)` | `GET /api/v1/orders/{id}` | 订单查询工具 |
| `get_seckill_list()` | `GET /api/v1/seckill/products/` | 秒杀活动查询工具 |
| `place_seckill_order(seckill_product_id)` | `POST /api/v1/seckill/{id}` | 下单执行工具 |

**实现要点：**
1. 定义 Tool schema（OpenAI Function Calling 格式或自定义 JSON schema）
2. 实现 ReAct 循环：`Thought → Action → Observation → ... → Final Answer`
3. 对话历史作为推理上下文持久化
4. 超时控制（最多 5 轮推理，防止无限循环）

**面试话术：**
> "不是调 API，是设计了推理 Agent。我定义了 4 个领域工具，让 LLM 自主规划多步推理路径，比如用户问『这个手机能秒杀吗』→ 先调商品工具查规格 → 再调秒杀工具查活动 → 综合回答。"

### 2.2 Prompt 工程：从单层 system prompt → 3 层模板体系

**当前状态：**
- [`SYSTEM_PROMPT`](app/services/chat_service.py:11) 是单层硬编码字符串
- [`PromptService`](app/services/prompt_service.py:13) 只做风格增强，没有结构化模板管理

**建议实现的 3 层模板体系：**

```
Layer 1: System Meta-Prompt（系统元提示）
  └─ 角色定义、能力边界、安全规则
  └─ 例如："你是闪电秒杀平台的 AI Agent，拥有 4 个工具..."

Layer 2: Task-Specific Template（任务模板）
  └─ 按意图分类的动态模板
  └─ 商品咨询 → {product_context} + {user_question}
  └─ 秒杀查询 → {seckill_context} + {time_info}
  └─ 订单查询 → {order_context} + {user_question}

Layer 3: Few-shot Examples + CoT（示例与推理链）
  └─ 每个工具附带 1-2 个 Few-shot 示例
  └─ 复杂场景走 CoT 链式推理
  └─ 例如："用户问余额→推理：没有余额工具 → 引导到订单查询"
```

**模板用 YAML 管理（[`app/services/prompt_templates.yaml`]）：**
```yaml
agent_system:
  role: "闪电秒杀平台 AI Agent"
  tools:
    - name: get_product_info
      description: "查询商品详细信息"
      parameters: { product_id: int }

task_templates:
  product_inquiry:
    system: "你正在帮助用户查询商品..."
    few_shot:
      - user: "这个手机多少钱？"
        assistant: "我先查一下商品信息。\n[调用 get_product_info]..."
```

**面试话术：**
> "系统化的 Prompt 工程。我设计了 3 层模板体系，用 YAML 管理全部模板，支持 Few-shot 示例和 CoT 推理链。不是写个 system prompt 就完事了。"

### 2.3 可观测性扩展：Agent 推理链路追踪

**当前状态：**
- [`trace.py`](app/middleware/trace.py:8) 只追踪 FastAPI HTTP 请求
- [`prometheus.py`](app/middleware/prometheus.py:3) 只暴露 HTTP 指标

**建议扩展：**

| 观测维度 | 实现方式 | Jaeger Span 结构 |
|----------|----------|------------------|
| **推理轮次** | 每轮 ReAct 循环创建一个 child span | `agent.reasoning.round_N` |
| **工具调用** | 每次 tool call 创建一个 span | `agent.tool.{tool_name}` |
| **工具延迟** | 记录工具执行耗时 | span attribute: `tool.duration_ms` |
| **意图分类** | 首次用户消息的意图识别 | `agent.intent.classification` |
| **Token 消耗** | 记录每轮推理的 token 数 | span attribute: `llm.tokens.total` |

**Prometheus 自定义指标：**
```python
agent_reasoning_rounds = Histogram('agent_reasoning_rounds', 'ReAct 推理轮次分布')
agent_tool_latency = Histogram('agent_tool_latency_ms', '工具调用延迟')
agent_intent_distribution = Counter('agent_intent_total', '意图分类计数', ['intent'])
```

**面试话术：**
> "AI 链路也能观测。我把 Agent 的每一轮推理、每一次工具调用都打上了 OpenTelemetry Span，跟已有的 Prometheus + Jaeger 无缝衔接。面试官问『Agent 卡在哪一步？』我可以直接看 Jaeger 的推理链路图回答。"

## 五、潜在风险与规避

| 风险 | 规避方案 |
|------|----------|
| LLM 幻觉：Agent 乱调用工具 | Tool 调用前加参数校验 + 输出约束 |
| 推理超时：复杂问题多轮循环 | 最大推理轮次 = 5，超时返回兜底回复 |
| 并发冲突：多个 Agent 同时操作 | 下单工具加分布式锁，复用秒杀现有幂等机制 |
| 成本失控：Agent 多轮调用 LLM | 每轮推理限制输出 token，缓存相似问题结果 |
